# Security and permissions

Rivet is experimental. The trusted supervisor, broker and SQLite ledger enforce exact operation grants; provider output, repository files, skills, MCP output and peer messages cannot grant permissions. Approval binds arguments, actor, scope, expiry and permission epoch, with durable intent before dispatch.

Built-in files reject unsafe paths/links and stale revisions. Worker checks use immutable source projections with recorded hashes. External processes require the qualified systemd, cgroup, bubblewrap and strict Landlock boundary; missing enforcement is an error. Git has a selected local mutation lane with helper/hook restrictions; this does not expose arbitrary remote Git operations.

Recovery records ambiguous effects as unknown. Never interpret cancellation as proof that no external work or billing happened. Backup/restore and repair require exact reviewed observations. Same-user hostile software, a compromised kernel, real power loss and all Linux platforms are not certified by these fixtures. File permissions and hashes are not encryption or adversarial tamper-proofing.

State and required audit evidence may contain sensitive metadata. Keep runtime state out of public reports; review all exported material. Ignore rules are not secret detection. No verified private security reporting contact or support policy is established. Do not post sensitive vulnerability details in public issues; an owner-selected private route is still needed before release.

[Verification](../planning/research/post-p3-verification.md) distinguishes this run from historical native checks. [Design history](../planning/security-and-recovery.md) records threat and crash matrices. Browser, desktop, mods, cross-project brokering and global permissions remain future work.
