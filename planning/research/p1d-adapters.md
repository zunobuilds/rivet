## Native profiles and credentials

Separate `ollama` (`/api/chat`) and `anthropic` (`/v1/messages`) configurations share the qualified reqwest/rustls client policy, exact request/destination broker permits and durable budget flow. Ollama normalizes streamed NDJSON text/object tool calls, done reasons and usage; no pull/install API or implicit compatibility fallback exists. Known cloud model identifiers are refused. A loopback daemon address alone cannot prove its backend processes data locally; no offline-processing guarantee is made for an arbitrary user-configured daemon.

Anthropic uses the explicitly pinned `anthropic-version: 2023-06-01` contract and sensitive `x-api-key` header. SSE blocks assemble fragmented arguments; duplicate blocks/calls, incomplete messages, unsupported content/stops and missing usage fail. Cache-read/creation input usage is included conservatively. Only fully validated calls reach complete proposals; chat still waits for terminal response validation before any dispatch. These are synthetic wire-contract qualifications, not a claim of live service/model compatibility or a newly fetched upstream API audit.

Credentials are ephemeral objects with opaque random references bound into the reviewed request. Swapping a credential under an existing grant is denied. No config/environment/keyring/file discovery or credential forwarding occurs. CLI `--ephemeral-key-stdin` reads one explicit non-terminal stdin line before review input; terminal key entry is refused to avoid echo. Keys are never printed or serialized; zeroize 1.9.1, promoted from the already-resolved graph, clears the owned secret on drop. This is not a claim that HTTP-library/allocator copies are universally erased. No keyring backend is qualified; there is no plaintext persistent fallback. Anthropic requires a supplied secret; remote HTTPS additionally requires positive explicit spend reservations.

## Brokered stdio MCP

rmcp 3.8.0 is pinned with defaults off, client + transport-child-process only. Its current latest protocol is 2026-07-28 with a different lifecycle; this initial profile explicitly pins the 2025-11-25 initialize handshake, rejects another negotiated version and never uses auto-discover/fallback or a network transport. The SDK owns protocol/call state. Its child-wrapper default read limit is 16 MiB and is not exposed for qualification, so use the same SDK AsyncRw transport with the supervised Tokio child and an explicit 1 MiB line limit. A framing decorator rejects duplicate JSON keys, invalid/oversized IDs, >1 MiB frames, >128 frames and >4 MiB aggregate server traffic. Application-generated execute payloads are bounded to 64 KiB before SDK encoding; initialize/list and denied server-request responses are bounded static protocol messages.

Servers run only inside the qualified systemd/bubblewrap/Landlock worker, with inherited strict restrictions, no host state/home/credentials/bus/network, explicit immutable source inputs and bounded scratch. The internal client has no provider/broker/ledger/secret authority. Sampling has no handler/capability and is refused; roots are empty and elicitation defaults to decline. MCP tool annotations/descriptions are untrusted and cannot grant capabilities. No package installation, ambient server search, remote transport or token passthrough is implemented.

Only explicitly enabled `[[mcp]]` entries are admitted (id, enabled, exact /usr/bin program/argv and literal source projection). The common `rivet:mcp` registry tool supports list and call. Review binds full server configuration, executable/argv/projection/profile, exact tool arguments and expected toolset digest. Each fresh worker lists the server's tools again; a changed schema/toolset or list-changed notification invalidates the call. Only one bounded page/32 tools/16 KiB descriptor set is supported. Results are capped at 32700 bytes; unsupported large/dynamic profiles fail. Generic server processes cannot modify the actual worktree through this profile; broader file/network MCP behavior would require a separate qualified grant/profile.

## Explicit skill text

`[[skills]]` entries require explicit enablement, id, project-relative SKILL.md path and pinned SHA-256. Nothing scans for skills, follows includes, installs or executes them. A brokered file-read approval and matching content pin are required before context inclusion. At most four enabled skills / 8 KiB each / 16 KiB aggregate fit within the shared context bound and step/deadline budget. Content enters as labeled untrusted user context and cannot replace user decisions or authorize tools. A changed pin stops before inference. Common credential roots (.ssh/.aws/.gnupg/.netrc and related files) are also protected by built-in path admission.
