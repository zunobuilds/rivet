## 1. Product boundary and interface

- **Rivet** is the primary standalone FOSS AI coding agent and hierarchy engine. Terminal-first chat experience broadly comparable to Codex CLI or Claude Code CLI; no requirement to resemble or fork Midnight Commander, no embedded file manager, no separate Git-management or Messenger interface, no embedded OpenCode runtime and no bespoke package manager. Keep practical agent tools for project-aware read/search/edit/patch/create/rename/delete, diffs, Git with permissions, terminal/build/test/lint/debug, new-project scaffolding, MCP, skills, context/session management, model setup, browser and native desktop app inspection. A file tool is not a file-manager UI.
- **Unrivet** is the separately maintained, optionally installed reverse-engineering/security-research add-on. It contributes firmware, binary, specialized device/network analysis, evidence/provenance, and optional `morluto/rea`. It reuses **all qualified installed Rivet tools and the same agent/model/hierarchy runtime** without duplicating assets. An add-on tool still requires its own task/project-specific permission. Removing Unrivet must not break Rivet.
- **New-project flow:** if Unrivet is installed, ask **"Enable Unrivet for this project? Yes/No"** at project creation, save it as editable per-project configuration; do not auto-enable or silently grant RE/device/network capabilities. With no Unrivet installed, simply create a Rivet project.
- Keep **Playwright/Chromium** in Rivet for browser automation/testing, plus qualified **Linux native application inspection** (accessibility/portals/native APIs with consent). No graphical Rivet frontend or embedded file manager is needed. Retain the post-1.0 macOS requirements: Playwright and actual macOS native application inspection; then Windows.
- **Local development:** two independent local Git repositories reported at `~/Projects/rivet-unrivet/rivet/` and `/unrivet/` on `main`, with no commits at the last user-shared check. User reports deleting the earlier GitHub repository. Do not assume any remote exists, commit or push, or access sibling/outside project files without the explicit permissions in their respective `AGENTS.md` files. `GITHUB_DOCUMENTATION_GUIDE.md` is part of both repo instruction setups.

## 2. Hierarchies, execution, autonomy, Cookbook

| Mode | Cardinality |
|---|---|
| **Solo** | Exactly 1 **Independent**; only mode in Rivet Minimal |
| **Pair** | Exactly 1 **Lead** + 1 **Operator** |
| **Crew** | Exactly 1 **Lead** + 1 **Reviewer** + **Operators >=1** |
| **Fleet** | Exactly 1 **Director** + **Leads >=1**, **Reviewers >=1**, **Operators >=1** |
| **Mesh** | Configurable peer mode; precise ownership semantics still need design |
| **Adaptive** | Configurable valid-mode selection; cannot violate fixed count rules |

- Configurable temporary specialists must respect the selected mode's fixed-count invariants or request a permitted mode change. Distinct agent roles need not have separate loaded models.
- Keep configurable **Concurrent / Shared Model / Model Relay** behavior; genuine multi-day authorized work with recoverable checkpoints, replay/idempotency protections, stop/pause/limits and robust cancellation. One supervisor, one trusted permission broker, **one durable task/message/audit ledger** (SQLite is the principal candidate), and one shared tool registry. Do not build a separate daemon, scheduler, message database, logger, resource dashboard or research-gateway service for every feature. Use process isolation only when warranted by privileges, crash boundaries or lifecycle.
- Human communications occur through the main terminal chat; preserve durable inter-agent messages, owner/leader routing, consent for forwarding important user decisions, acknowledgment, and evidence references. Human file edits are informational, not elevated instructions.
- **Cookbook** recommends models, role allocations, resource budgets and Efficient/Balanced/Ambitious priorities. Reuse qualified `llmfit` hardware/model-fit data when useful instead of building a redundant catalog; Rivet computes whole-hierarchy feasibility and handles local/remote budgets, serial queues, relay and explainable slow/unsupported warnings. Automatic optimization beyond this remains **deferred**, not a mandatory first-release requirement. Benchmark only on explicit user authorization.

## 3. Absolutely no default model download

- **No AI model weights are preselected, downloaded or installed by default** in **any** Rivet or Unrivet preset. No automatic local inference runtime (Ollama, llama.cpp, etc.) is installed merely by selecting a preset, and no particular Qwen 30B model is compulsory. The user chooses an existing provider/endpoint or explicitly elects to acquire a runtime and model; local and cloud providers are optional alternatives, not forced bundles.
- Setup/settings, configuration review, repair/status and manual/offline administrative functions work without model credentials or weights. A coding inference session needs a compatible configured provider, but **absence of a model must not trigger an automatic download, cloud fallback, upload, paid call or concealed account setup**. Setup can report "provider not configured" honestly; don't declare inference-ready until actually checked.
- User can configure permitted local↔cloud switching, with cost, quota, privacy and data-transfer warnings. Model selection is independent from installer preset, agent mode and execution policy. No benchmark without opt-in.

## 4. Install and tool ownership

- Rivet and Unrivet each have independent **Minimal / Recommended / Full / Custom** presets. Rivet Minimal supplies useful **Solo** coding and no hierarchy modes; Rivet Recommended includes hierarchies, Playwright and qualified Linux app inspection. Full is qualified broader capabilities, **not all catalog entries installed**. Unrivet presets are separate RE tool packs. **Portable is always the recommended location**, System is explicit opt-in and never recommended, no Hybrid.
- The historical catalog remains **IDs 1–109** for inventory/provenance (models, libraries, system facilities and custom obligations count too). Accepted tool integrations do not imply mandatory downloads or that all 109 are independent applications. For each tool: first use verified available installs where consistent with location mode, or offer a managed version after authorization, or leave it absent. No unwanted package installs. Extra tools selected by project/preset/type only.
- Rivet's accepted specialist CLI adapters include **ast-grep, Difftastic, Ruff, actionlint, ShellCheck, fd, Watchexec, Hyperfine, yq, uv**; use language/task-aware invocation, not every binary in every preset. Unrivet's accepted RE adapters include **checksec, TLSH, firmwalker, capa, FLOSS, ssdeep**. Rivet's registered tools remain available to Unrivet-enabled projects under their permissions.
- **Approved capability deduplication strategy** (exact per-platform package membership remains to be qualified): prefer YARA-X over original YARA by default subject to rule compatibility; TLSH primary and ssdeep on demand; Binwalk first and Unblob as fallback; choose one qualified SquashFS implementation by format; ripgrep standard, fd optional, ugrep/tree non-default; single hex/hash capability implementation; jq for JSON and yq for multi-format where useful; checksec implements original ELF-hardening item; Syft+Grype for regular SBOM/vulnerability workflow, CVE Binary Tool specialist optional; Ghidra/Rizin complementary, angr advanced optional; Difftastic for source and diffoscope for binaries/packages; language-specific lint tools only when relevant; Watchexec/Hyperfine only when useful; install archive/compression helpers only if actual recipes require them; optional Ghidra/JDK, REA, capa/FLOSS/angr according to qualified Unrivet features. No presumption that these tools are interchangeable in all cases: validate formats, fixtures, security and fallback coverage before removing a selected implementation.
- Rivet's human-facing reporting is **lean**: ordinary task results, diffs, status and exportable Markdown/JSON plus durable required audit logs/checkpoints. Unrivet keeps specialist reproducible evidence reports and provenance. No separate dashboard/report designer. The earlier "reporting" question D86 is resolved only to this bounded scope; do not remove security/evidence data.

## 5. Lean packaging, compressed storage, safe updates

1. **Avoid downloading unused assets**: optional install on demand; no model bundles. Reuse matching immutable dependency/tool copies across Rivet and Unrivet and multiple projects within an app-managed Portable installation root; separate project data/permissions.
2. Favor qualified upstream slim distributions and deterministic source-build/strip-debug options if justified. Compress **downloads** via zstd/xz archives as supported, but explain that extraction restores normal installed size. Do not strip required licenses, notices, runtime modules or security receipts. Never change original user research evidence bytes.
3. **aqua + uv are the preferred existing upstream-aware tooling** to prototype, not an invented general-purpose package manager: aqua for selected pinned CLI release assets (when verified portable and supported), uv for isolated Python tools. Fallback acquisition needs separately justified policy. Neither may bypass verification or authorized installation boundaries.
4. Proposed update transaction adopted as product design: an authorized policy checks **known original upstream projects**; show version/license/footprint/changes; download to staged app-owned storage; verify checksums and available trusted signatures/attestations, exact OS/ABI and dependencies; smoke-test without project access; optionally reproducibly optimize a **derivative** artifact; atomically activate a pinned immutable version when no task is using old version; retain rollback. Updates to CVE databases, rules, model weights and plugin APIs have separate compatibility/consent boundaries. Missing upstream signatures cannot be silently invented, and self-generated checksums alone do not prove authenticity. No automatic unapproved updates.
5. **UPX and compressed SquashFS runtime storage are experimental, disabled by default**, because they may harm portability, start time, memory sharing, security tooling and verification. A successful upstream update must be independently tested for each locally transformed binary. Measure downloaded, installed, runtime and peak/cache sizes separately; no claimed numerical savings before testing.

## 6. Release and execution gates

- Small useful **pre-1.0** milestones are expected; **Rivet 1.0.0 = mature Linux-only release**, not the first feature-rich prototype. macOS with Playwright + native macOS application inspection follows, then Windows. Exact version numbers and timelines are not locked.
- **Proposed staged engineering order**, *not authorization to begin*: P0 authoritative spec/repo setup; P1 functional Solo coding agent; P2 durable recovery; P3 hierarchies/shared model/relay; P4 Playwright/Linux native app tests; P5 Unrivet add-on/opt-in/RE fixtures; P6 updater, shared store and measured size optimization; P7 Linux v1.0 qualification. Adjust implementation milestones without redefining approved final product vision.
- **Mandatory stage gate:** each future implementation stage must receive separate explicit user approval for scope and external effects, then evidence-backed tests/report and durable checkpoint, then **STOP**. Ordinary usage-status check-ins are independent and may continue automatically according to each repo's `AGENTS.md`. No stage approval is inferred from choosing architecture, accepted tools or this documentation refresh.
